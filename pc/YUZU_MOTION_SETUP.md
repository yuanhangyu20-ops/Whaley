# Yuzu 体感（DSU / Cemuhook）配置 — 傻瓜式步骤

> ## ⚠️ 最重要的一条：必须先启动游戏！
>
> **Yuzu 的 DSU 客户端只在游戏运行时才创建。**
> 在「模拟 → 设置 → 控制」界面里，体感文档示意图**永远不会动** ——
> 这不是配置错误，是 Yuzu 的设计：设置界面的预览不初始化 CemuhookUDP。
>
> 判断体感是否生效，**只能看桥接窗口的 `DSU客户端=1 推送=xxxx`**，
> 或者进游戏实测（塞尔达射箭最直观）。

> 前提：桥接已启动，窗口里能看到
> `[DSU] 服务端已启动 → udp://0.0.0.0:26760`

---

## 一、先确认桥接端的 DSU 是活的

在电脑上开 PowerShell，粘贴运行：

```powershell
cd D:\devkit\wifipad\pc
python -c "import socket,struct,zlib; H=struct.Struct('<4sHHIII'); h=H.pack(b'DSUC',1001,22,0,0,0x100000); s=socket.socket(2,2); s.settimeout(2); s.sendto(h,('127.0.0.1',26760)); print('DSU OK:', len(s.recvfrom(99)[0]), 'bytes')"
```

- 输出 `DSU OK: 22 bytes` → **服务正常，继续第二步**
- 报 `timeout` → 桥接没启动，先在 `pc` 目录跑 `python Yuzu_Bridge.py`

## 二、手机端打开体感

1. 手机上打开 **WifiPad**
2. 点顶部中间**齿轮**打开抽屉
3. 找到 **「体感」** 开关 → **打开**（副标题应显示 `陀螺仪 + 加速度计 → DSU`）
4. 点 **「开始连接」**

桥接窗口应该出现：

```
[RX] 手机已连接 ← 10.99.179.132:xxxxx
[状态] 手机在线 60pps  模式=Switch 体感=开  DSU客户端=0 推送=0
        KEY=-                  L=(+0.00,+0.00) R=(+0.00,+0.00) TRIG=0.00/0.00
        GYRO=(+0.00,+0.00,+0.00) rad/s  ACC=(+0.00,+0.00,+1.00) g
```

**关键检查**：
- `体感=开` ✓
- `ACC=...+1.00 g` ✓（手机平放时应是 z 轴 1g）
- 晃动手机时 `GYRO` 的数值会跳动 ✓

> 如果 `体感=关`，说明开关没打开，回第 3 步重开。

## 三、Yuzu 里配置 DSU

### 3.1 打开控制器设置

**Yuzu 主界面 → 上方菜单 `模拟(E)` → `设置`**

左侧列表点 **`控制`**

### 3.2 配置 Player 1（按键/摇杆）

| 项目 | 选择 |
|---|---|
| **输入设备** | `任意控制器`（或 `Pro Controller`）|
| **输入方式** | `自动` |

点 **「配置」** 按钮 → 弹窗里应能看到：

```
Xbox 360 Controller for Windows
```

这就是桥接创建的虚拟手柄。按提示依次按键即可。

点 **「确定」** 保存。

### 3.3 开启体感（关键步骤）

**同一个「控制」页面**，滚动到下方找到 **「体感 / Motion」** 区域：

```
┌─ 体感 ────────────────────────────────┐
│  输入源:   [ 无            ▼ ]        │   ← 点这里
└───────────────────────────────────────┘
```

1. 点 **「输入源」** 下拉框
2. 选择 **`DSU 客户端`**（英文版是 `DSU Client`）
3. 选完后下方会多出两行：

```
   服务器地址:  [ 127.0.0.1        ]     ← 必须填 127.0.0.1
   服务器端口:  [ 26760            ]     ← 默认就是 26760
```

4. **地址填 `127.0.0.1`**（不是局域网 IP！桥接和 Yuzu 在同一台电脑上）
5. 端口保持 `26760`
6. 点 **「确定」** 保存

### 3.4 看到什么才算成功

**必须先启动一个游戏**（Yuzu 主界面 → 双击游戏），然后看桥接窗口：

```
[DSU] 收到包 type=0x100000 (VERSION_REQ) from 127.0.0.1:xxxxx
[DSU] 收到包 type=0x100100 (PORTS_REQ)   from 127.0.0.1:xxxxx
[DSU] 收到包 type=0x100200 (DATA_REQ)    from 127.0.0.1:xxxxx
[DSU] Yuzu 已订阅 ← 127.0.0.1:xxxxx  (共 1 个客户端)
```

之后每 5 秒的状态行：

```
[状态] 手机在线 60pps  模式=Switch 体感=开  DSU客户端=1 推送=4559
```

**判断标准**：

| 桥接窗口 | 含义 |
|---|---|
| `DSU客户端=1 推送=4559` 且不断增长 | ✅ **体感已接通** |
| 只有 `DSU客户端=0 推送=0`（游戏已启动）| ❌ 地址填错，回 3.3 重配 |
| 只有 `DSU客户端=0`（**没启动游戏**）| ⚠️ 正常现象，先启动游戏 |

> ⚠️ **Yuzu 里不会显示"绿色图标"**。Yuzu 的 DSU 没有连接指示灯，
> **唯一的成功标志是桥接窗口的 `DSU客户端=1` + `推送` 持续增长**。

## 五、常见问题

### Q1: Yuzu 的输入源下拉框里没有 "DSU 客户端"

- 你的 Yuzu 版本太旧，更新到 EA / 主线最新版
- 或者下拉框里叫 **`Cemuhook`**，选它也是一样的

### Q2: 桥接一直显示 `DSU客户端=0`

排查顺序：

1. 地址是不是 **`127.0.0.1`**（很多人填成电脑局域网 IP，这是最常见的错误）
2. 端口是不是 `26760`
3. 桥接窗口有没有 `[DSU] 服务端已启动`
4. 端口被占用？运行：
   ```powershell
   netstat -ano | findstr :26760
   ```
   应该只有桥接的 python 进程

### Q3: 体感数据在跳但游戏里没反应

1. 确认游戏真的支持体感（不是所有游戏都用）
2. Yuzu 里 **`模拟` → `设置` → `控制` → `体感`** 再看一遍输入源是否保存成功
3. 有些游戏需要在游戏内菜单**手动打开体感选项**

### Q4: `GYRO` 一直是 0，但 `ACC` 正常

手机没有陀螺仪，或者系统禁用了传感器权限。
检查：手机设置 → 应用 → WifiPad → 权限 → 身体传感器/运动数据 → 允许

### Q5: `ACC` 的 z 不是 1.00g

- 手机没平放（倾斜时分量会跑到 x/y）
- 或者 `体感=关`，此时桥接会强制上报 (0,0,1g) 静止姿态

## 六、两种模式的区别

抽屉里的 **「Switch 模式 / Xbox 模式」** 开关只影响**按键**，与体感无关：

| 模式 | 手机 A 键 | 适用 |
|---|---|---|
| **Switch 模式**（默认）| → 虚拟 B → Yuzu 的 A | Switch 游戏，按 A 是"确认" |
| **Xbox 模式** | → 虚拟 A | 想一一对应时 |

切换后桥接窗口的 `模式=` 会立即变化，不用重启。

## 七、手柄在游戏里完全没反应（重要坑）

### 症状
- Windows 里手柄正常（XInput / 游戏控制器面板都能看到）
- Yuzu 设置界面能看到 `Xbox 360 Controller`
- **但游戏里按任何键都没反应**

### 根因
Yuzu 的每个按键绑定记录的是 **SDL 设备 GUID**：

```
player_0_button_a="engine:sdl,port:0,guid:030000...7801,button:1"
```

如果你之前用**实体 Xbox 手柄**配过 Yuzu，这个 GUID 就是实体手柄的。
ViGEm 虚拟手柄的 GUID 是**另一个**：

| 设备 | SDL GUID |
|---|---|
| 实体 Xbox 360 手柄 | `030000005e040000130b000023007801` |
| **ViGEm 虚拟手柄** | `030003f05e0400008e02000000007200` |

GUID 不匹配 → Yuzu 一直在监听一个不存在的设备。

### 修复（一条命令）

```powershell
cd D:\devkit\wifipad\pc
python fix_yuzu_guid.py           # 自动检测并改写 23 处绑定
```

然后**重启 Yuzu**（配置只在启动时加载）。

先检查不改：

```powershell
python fix_yuzu_guid.py --check
```

### GUID 是稳定的
虚拟手柄由 ViGEmBus 创建，VID/PID 固定（045E/028E），
所以 GUID 每次重建都一样 —— **修复一次永久有效**。

## 八、体感（DSU）什么时候才真正建立连接

用 DSU 包级追踪实测得到：

| 场景 | 桥接显示 | 说明 |
|---|---|---|
| Yuzu 主界面 | `DSU客户端=0` | 正常，客户端未创建 |
| **打开设置→控制** | `DSU客户端=0` | **正常**，设置界面不初始化 UDPClient |
| 游戏在标题画面 | `DSU客户端=0` | 正常，游戏还没请求体感 |
| **游戏中举弓/进体感场景** | `DSU客户端=1 推送=xxxx` | ✅ 真正激活 |

**结论**：不要用 Yuzu 的设置界面判断体感是否生效。
唯一可靠的判断是桥接窗口的 `DSU客户端=1` 且 `推送` 持续增长，
而它通常要等你**真正在游戏里用到体感**时才会出现。

### 不想进游戏时怎么验证

```powershell
python motion_viewer.py
```

看到数值随手机倾斜实时变化 → 手机到电脑的体感链路 100% 正常。

## 九、DSU 协议细节（借鉴 PhoneGyro）

本项目 DSU 编码器在排查体感不准时，参照了开源项目
[MrHoustonOff/PhoneGyro](https://github.com/MrHoustonOff/PhoneGyro)（MIT 协议）
以及它的 `docs/motion-pipeline.en.md`。以下是从中确认并落地的关键点：

### 9.1 之前实现的三个错误

| 项目 | 之前（错） | 正确 | 后果 |
|---|---|---|---|
| magic | `DSUC` | **`DSUS`**（服务器→客户端）| 客户端可能不认该包 |
| length 字段 | 整包长度 100 | **payload+4 = 84** | 解析长度错乱 |
| 消息类型 | 0x100001 作版本响应 | **请求/响应共用 type** | 握手语义错 |

### 9.2 正确的 pad data 布局（80 字节 payload）

```
p[0]      slot                0
p[1]      slot_state          2 = 已连接
p[2]      model               2 = 完整陀螺仪手柄
p[3]      conn_type           2 = 无线
p[4:10]   mac
p[10]     battery             5 = 满电
p[11]     is_active           1
p[12:16]  packet_number
p[20:24]  四根摇杆轴（128=中位）
p[48:56]  timestamp  u64 微秒  ← 客户端按此差值积分角速度
p[56:68]  accel      f32×3，单位 g
p[68:80]  gyro       f32×3，单位 deg/s
```

### 9.3 坐标系与符号

PadTest 验证过的 DSU 约定是**平放时 `AccY = -1 g`**（Y 轴指向重力方向）。
手机坐标是 (X右, Y上, Z屏幕外)，需转换：

```
DSU_Acc  = (-mx, -mz, -my)
DSU_Gyro = ( mgx,  mgz,  mgy)
```

其中 `RotY`、`AccX`、`AccZ` 还要取反（PhoneGyro 的 `DSUYawSign`/`DSUAccSign`），
否则会出现**偏航镜像**和**保持倾斜角度时缓慢回爬**。

### 9.4 其它借鉴的设计

- **No gyro smoothing**：文档明确"任何对角速度的低通都会增加延迟，客户端积分后会超调"。
  所以我们直接发原始传感器值。
- **时间戳是"积分时钟"**：步进必须等于速率平均所覆盖的间隔，否则积分有误差。
  本项目用 `time.monotonic()`，保证严格递增且不受系统时钟跳变影响。
- **发送率**：手机 120Hz、DSU 120Hz，减少每一级最多 16.7ms 的等待。

### 9.5 尚未移植的部分

PhoneGyro 的**姿态锚定**（`motion/attitudeanchor.go`）能压制 DSU 客户端积分漂移
（60 秒快速运动：无修正漂移 34.5°，有修正 0.1°）。它需要手机提供四元数
（`deviceorientation`）并在服务器维护一个"客户端将达到的姿态"模型，工程量较大，
暂未实现。若后续发现长时间玩有累积偏移，再移植。
